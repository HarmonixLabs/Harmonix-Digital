Harmony AI Demo Page – Detailed Design & Next Steps

Overview: This document outlines the redesigned Harmony demo page – including its content, layout, and functionality – and queues up next steps for building out the full dashboard and deployment interface. The demo page will showcase six core AI agents in an interactive chat-based experience, allowing users to see each agent’s capabilities and even simulate or execute tasks in real-time. We also cover how the demo toggles between simulation and live API modes, the UI/UX layout (with a Figma-style wireframe), and considerations for agent switching, branding, and conversion (Stripe/crypto payments). Finally, we detail the plan for what happens after a user decides to deploy an agent, i.e. integrating into their personal dashboard.

Six Core Agents in the Public Demo

The demo will feature six flagship AI agents, each with a distinct role and persona. Users can select any of these six to interact with (via a tab or carousel selector). Each agent’s chat persona will introduce itself and guide the user on how it can help their business, effectively “selling” its own value. The six core agents to enable are:
	1.	SŌL (Harmony Brain) – Strategic orchestrator & recommender. This is the master coordinator agent that harmonizes strategies across other agents. SŌL can answer high-level strategy questions and recommend which agents or actions to deploy for a given business goal.
	2.	CA$H (AI Sales Closer) – Lead capture & sales agent. An agent specialized in sales: it greets leads, qualifies them, answers product questions, and can schedule or even book sales calls. In demo it can simulate capturing a lead’s info and setting an appointment.
	3.	ECHO (Content & Social Storycaster) – Content planner & creator. Generates content calendars, social posts, captions, blog outlines, and even short-form video ideas. Great for marketing teams – it can show a week’s worth of posts or draft a catchy caption in the chat.
	4.	FLOW (Ops Optimizer) – Operations & SOP optimizer. An agent that maps out Standard Operating Procedures and suggests workflow automations. It can take a task (like onboarding a new client) and break it into a step-by-step SOP or recommend software integrations to streamline operations.
	5.	KAIROS (Project & Time Manager) – Project timeline and scheduling guru. This agent assists with project management – creating timelines with milestones, identifying task dependencies, and syncing with calendars (in live mode). In demo it might produce a Gantt-style timeline for a sample project.
	6.	CONCIERGE (Client Success) – Onboarding, support, and retention. Acts as a client success manager. It can answer common FAQs, guide a new user through onboarding steps, check in on customer satisfaction (NPS surveys), or handle support queries.

UI Note: Each agent will be represented with an avatar or icon and a name. When selected, the agent’s bio popover (accessible via hovering or clicking the avatar) will show a short description, key skills, and any integrated tools (e.g. if the agent connects to Slack, HubSpot, etc. in live mode). Any other AI agents beyond these six will appear in the interface as “Locked” (grayed out) with a tooltip like “Join Waitlist to Unlock” – encouraging users to sign up for future access.

Demo Modes & API Behavior (Sim vs. Live)

The demo page will support two operational modes for how agents execute tasks and API calls, selectable with a toggle (default is Simulation Mode):
	•	Simulation Mode (SIM) – Default and safe. In this mode, the agents respond with deterministic, scripted outputs and use mock integrations rather than real API calls. This allows a smooth demo without needing the user’s credentials. For example, CA$H might “schedule a meeting” by calling a fake calendar API endpoint (e.g. a Pipedream webhook) that returns a canned success response. All external actions (CRM entry, social media post, email send, etc.) are simulated with realistic dummy data. We will tag all such interactions clearly as “Demo Data” or “SIMulated” in the UI. This protects both the user and external systems from any unintended effects during the public demo.
	•	Live Mode (LIVE) – Connected to real APIs (opt-in). In Live mode, the agents perform real actions using the user’s integrations, but this is only enabled if the user proactively connects their accounts. For example, if a user provides a HubSpot API key or OAuth for Google Calendar in the demo, CA$H could actually create a contact or calendar event in their system. Live mode can be toggled on a per-integration basis: e.g. a user might connect Slack and test the CONCIERGE agent sending a real Slack message, while other actions remain simulated. Safe-guards will be in place: certain potentially disruptive actions (like mass emails or live social posts) will require a confirmation step even after integration. We will also apply rate limiting and redact any personal identifiable info by default (unless user opts in) during the demo.

Mode Toggle UI: The top bar will include a clear toggle or switch labeled Simulation / Live. In SIM mode, a subtle “Demo Mode” watermark or badge is shown on the chat and any generated content. In LIVE mode (after credentials are provided), the badge might say “Live” or the toggle might turn green. If no credentials are connected, toggling to Live will prompt a modal for the user to connect accounts (OAuth flow or API key input, depending on the service). The user can connect multiple integrations in this modal (e.g., Connect HubSpot, Google Calendar, Slack, etc.), after which those specific integrations become active for the agents to use.

API Handling: Under the hood, when in Simulation mode, all agent tool usage routes to pre-defined stub endpoints (likely implemented via Pipedream or mock server) which return example data. For instance:
	•	POST /demo/intake – (Simulated) capture lead or profile info (for CA$H or CONCIERGE).
	•	POST /demo/strategy – returns a mock strategy plan object (for SŌL’s planning or ECHO’s content plan).
	•	POST /demo/execute – logs the execution of a task (like “Meeting scheduled” event).
	•	POST /demo/kpi – returns some made-up KPI increments (e.g., “+1 lead” or “+1 post queued”).

In Live mode, actual API calls will be made to services via our backend or integration layer (for security, the front-end likely sends to our server which then interacts with e.g. HubSpot API, Slack API, etc., using the stored credentials). The demo page will clearly differentiate these in the execution log (e.g., a label “SIMulated call” vs “LIVE API call”).

Payments in Demo: To allow users to explore the purchase flow without risk, any payment interactions in demo will use sandbox/test mode. For example, if the user clicks “Deploy Agent” in the demo, they might go through a Stripe test checkout (with dummy card numbers) or a NowPayments crypto test flow. This gives a feel for the payment process without charging real money. Only when the user is in their actual account (post-signup) and confirms a real purchase will we use live payment processing – more on this in the “Next Steps” section.

Layout & Components – Module Wireframe

Figma-style wireframe of the Harmony demo module layout. The top bar contains the agent selector and controls; the main area is split into a left chat panel (conversation UI), a center panel (strategy canvas or timeline view), and a right panel (integration status & CTAs). A collapsible footer drawer holds logs and notes.

The demo page layout is designed to let the user chat with the selected agent on one side, while viewing the agent’s strategy and execution output on the other. Here’s a breakdown of the key UI components (corresponding to the wireframe above):
	•	Top Bar: Stretched across the top of the page, this contains:
	•	Agent Selector: A horizontal list of the 6 agent avatars/names. The current active agent is highlighted. Clicking on a different agent switches the interface (see “Switching Agents” below). Each avatar can be hovered for a quick bio (popover with description and use cases).
	•	Mode Toggle: A switch or button to toggle Simulation vs Live mode (with an indicator as described earlier).
	•	Session Controls: e.g. a “Reset Session” button (to clear the chat and start that agent’s demo over fresh), and a “Save Transcript” or “Export Chat” option (allowing the user to download or copy the conversation and strategy outputs).
	•	Call-to-Action (CTA): A prominent button on the top right, such as “Deploy Agent” (if that agent is available to install) or “Join Waitlist” (if not available). This triggers the conversion flow (signup or purchase). We might dynamically change the CTA text based on agent status – e.g. for core agents it says “Deploy to My Dashboard”, for locked ones “Reserve Spot” or “Join Waitlist”.
	•	Left Panel (Chat Console): This is a scrollable chat interface similar to ChatGPT’s. It shows the conversation between the user and the agent. Each agent will have a slightly different persona/tone, reflected in how it chats. For example, ECHO might use a friendly, creative tone when suggesting social media content, whereas FLOW might be more analytical. The chat panel includes:
	•	Message Stream: Messages appear as bubbles or blocks (agent messages might be in a colored background with the agent’s name/avatar, user’s messages in a neutral background). Agents can also send rich text or small attachments (e.g., ECHO might output an image thumbnail or a snippet of a content calendar, which could appear as an attachment card in the stream).
	•	Message Input Composer: At the bottom of the chat panel, the user can type messages or click suggested prompts. We will provide a few one-click prompt buttons for each phase (for example, “Discover” or “Show Strategy” or “Execute Plan”) to guide the demo. There could also be preset “Persona tones” or styles the user can toggle for the agent (though this might be more advanced – e.g., SŌL could have modes like “Strict” vs “Creative”).
	•	Progress Indicator: Just above the chat or integrated into it, there may be a subtle progress bar or step indicator showing the phase: Discovery → Strategy → Execution. This helps users understand where they are in the agent’s process (especially for agents that follow a multi-step demo script).
	•	Center Panel (Strategy Canvas & Timeline): The middle section displays the agent’s structured output – essentially the “work product” the agent is generating:
	•	Strategy Canvas / Plan: For agents like SŌL or ECHO, this could be a visual outline or canvas. For instance, SŌL might display a strategy document: objectives, recommended steps, resources, KPIs. ECHO might show a content calendar view or list of post ideas. This could be an interactive area where the user can click through different tabs: e.g., Strategy Plan, Generated Content, Timeline.
	•	Execution Timeline: When the agent starts executing tasks (especially in the Execution phase), this panel might switch to a timeline mode. For example, KAIROS’s timeline (Gantt chart) could show tasks scheduled over days. CA$H might show a mini sales pipeline or timeline of interactions (lead created → email sent → meeting booked).
	•	Artifacts and Outputs: If an agent produces files or specific outputs (like a draft email, social post caption, or PDF report), those can be listed here as downloadable artifacts. Perhaps a tabbed sub-section: one tab for “Plan/Timeline” and another for “Artifacts/Outputs”.
The center panel is essentially a dynamic content area that changes based on agent and phase: it could be a timeline, a table, a list of tasks, or even a canvas with nodes (for FLOW’s SOP diagrams). It’s meant to complement the chat by giving a bird’s-eye view of what the agent is working on or proposing.
	•	Right Panel (Metrics & Actions Sidebar): The rightmost column serves as an info and action sidebar:
	•	Live KPI Counters: At the top, we can show a few key metrics relevant to the agent, updating in real-time (or simulated real-time). For example, for CA$H we might display “Leads Captured: X”, “Meetings Booked: Y” as counters that tick up when those events occur. For ECHO, maybe “Posts Generated: X”. This gives a sense of tangible results.
	•	User Data Capture Form: Since many agents need some user context (industry, goals, budget, etc.), we include a small form or card here where the user can input (or edit) their demo profile. This might have fields like Industry, Top Goal, Budget Range, etc., and possibly a file upload or link input if the user wants the agent to analyze an example (for instance, uploading a sample SOP for FLOW to optimize). The agent can read these inputs to tailor the conversation. In Simulation mode, we might pre-fill it with a fictional company profile (“Acme Corp – SaaS – $1M budget”) to show how it works.
	•	Integrations Panel: A section showing icons for each integration (CRM, Calendar, Slack, etc.) with their status: either Connected (if user connected it in Live mode) or Locked/Not Connected. The user can click here to manage integrations, which opens the connection modal. This area basically advertises what the agent could connect to for full functionality.
	•	Conversion CTA Area: Towards the bottom of the sidebar, a dedicated call-to-action panel will prompt the user to take the next step. If the user has not signed in or the agent is not yet deployed, it might say “Deploy this Agent to your Business” with a brief benefit statement, and a button. Alternatively, if the agent is a premium one or not launched, it might say “Reserve this Agent” or “Join the Waitlist for full access”. We want this panel highly visible once the user has seen enough of the demo.
	•	Bottom Drawer (Logs & Notes): Along the bottom (fixed position) there will be a collapsible drawer (perhaps hidden by default with a small tab to expand). This contains:
	•	Activity Logs: A detailed log of the agent’s behind-the-scenes actions (useful for power users). This is where we show each API call the agent attempted, the decision branches, any redactions, etc. It’s like a debug console but user-friendly (for transparency).
	•	Notes/CRM Preview: The agent might be compiling notes or a CRM entry based on the chat. For example, CA$H could auto-generate a lead summary note. This sub-section would show “Here’s what will be saved to your CRM” or “Demo transcript summary”. It helps build trust by showing how data is handled.
	•	Compliance & Consent: Some text about data usage in demo, a reminder that it’s sample data unless they go live. Possibly a checkbox “I consent to use of my input data for demo purposes” (especially if they engage live mode and enter personal data).

Responsive Design: On smaller screens (mobile/tablet), the layout will stack: the chat might become full-width with a toggle to view the strategy/outputs. The top bar agent selector might turn into a dropdown. The bottom drawer might become a modal.

Switching Between Agents in One Session

Users can switch agents on the fly during the demo session to explore different capabilities. The design will allow this seamlessly, while managing state carefully:
	•	Preserved State per Agent: Each agent’s conversation and progress are kept separate. For example, if the user chats with SŌL, then switches to ECHO, then back to SŌL, they should see their previous SŌL chat history and SŌL’s strategy canvas as they left it. We achieve this by maintaining an independent session context for each agent tab.
	•	Shared User Context: Some basic user inputs (like the company profile info in the sidebar) can be shared across agents so the user doesn’t need to re-enter them. For instance, if you entered your industry and goal while talking to SŌL, then switched to FLOW, FLOW will already know those details. However, more complex state or the plans generated are not shared between agents (to avoid cross-contamination of conversations).
	•	Isolated Execution: Actions taken by one agent do not carry over to another. If ECHO “scheduled 5 posts” in its context, and then you switch to CA$H, CA$H’s metrics start from its own context (it doesn’t suddenly have 5 posts). This keeps each agent demo coherent.
	•	UI Behavior: Clicking an agent in the top bar immediately switches the main view to that agent’s chat and panels. We can add a quick transition animation (like sliding panels or fading) to make it feel smooth. The active agent’s icon enlarges or is highlighted. If an agent has unseen activity (e.g., you left one agent running and it finished a plan), we might show a small notification dot on that agent’s icon to draw the user back.
	•	Reset and Exit: The “Reset Session” button only resets the currently active agent’s session (we will confirm with the user before wiping it). If the user wants to start all over, they’d have to reset each agent or refresh the page. We may also provide an “End Demo” or “Start Over” option that clears all and returns to a default state (perhaps selecting SŌL by default as the first agent).

Technical Note: Each agent could have its own WebSocket or session ID if the backend is maintaining conversational context. When switching, we pause any background generation (if an agent was mid-response, maybe we either cancel it or let it finish in the background but not show until user returns). The separate contexts ensure that prompts from one agent do not bleed into another agent’s chain-of-thought.

UI/UX Design References & Style

We want the demo to feel modern, slick, and on-brand for Harmony. A few design references and principles to guide us:
	•	Inspiration from ChatGPT and modern SaaS UIs: The chat interface will take cues from familiar messaging apps and AI chat UIs (like ChatGPT’s conversational flow). The overall page layout (with multiple panels and an activity log) is inspired by productivity tools like Notion, Linear, or project management dashboards. We combine the conversational UI with a dashboard feel.
	•	Harmony Brand Aesthetics: The color palette will align with Harmony’s “rooted futurism” vibe – likely deep greens/teals (forest) or midnight blues for backgrounds, accented with gold or neon highlights for interactive elements. We’ll use a clean sans-serif font like Inter or Open Sans for body text, and a more distinctive font like Satoshi or Poppins for headings and agent names. Cards and panels will have slightly rounded corners (border-radius for a friendly, modern look) and possibly subtle shadow or glow effects (e.g., the active agent panel could have a faint gold glow).
	•	Light & Dark Modes: The design should work on both light and dark backgrounds. Initially, we can default to a light theme with white or very light gray chat bubbles and darker text. But a dark mode toggle (or auto based on system) would be great, where backgrounds go dark and text/icons adjust accordingly. This is important for accessibility and user preference.
	•	Micro-Interactions: We’ll incorporate smooth animations – for example, when an agent “thinking” or generating a response, show a typing indicator with three dots, or an animated icon. When metrics update, have them count up with a short animation. Hover effects on buttons and agent avatars (e.g., slight scale-up or tooltip on hover) will make it feel polished.
	•	Consistency & Reusability: All UI components (buttons, cards, tabs, etc.) will follow a design system to ensure consistency. We have an initial UI kit that includes typography, color scheme, spacing/grid, and component styles ￼. This means using a consistent style for things like primary CTA buttons (maybe gold background with dark text, or vice versa), secondary buttons, form inputs, etc., all documented so developers have a clear reference.
	•	Accessibility: We aim for WCAG AA contrast compliance – ensuring text is readable against backgrounds (especially the chat text vs bubble background). All interactive elements will be keyboard navigable (e.g., user can tab through the agent selector, press Enter to select an agent, etc.). ARIA labels will be added for screen readers (announcing things like “Message sent by SŌL” or “Lead capture form”). Also, providing alternatives like caption text for any visual output from agents.

In summary, the UX should feel engaging but not overwhelming – a new user can easily follow what’s happening (thanks to the structured center panel and progress indicators), while a power user can dig into logs and data. The visual style should reinforce trust and innovation: a blend of enterprise dashboard and futuristic AI assistant.

Next Steps: Full Dashboard & Deployment Interface

Once the public demo page is live and users are excited by an agent, what happens next is crucial. We need to convert that interest into actual deployed agents on the user’s account. Here we outline how the full Harmony dashboard and agent deployment process will work, integrating payments and account creation.

1. Conversion from Demo to Account: When a user clicks “Deploy” (or “Sign in to Deploy”) on the demo page, we’ll initiate an onboarding flow:
	•	If the user isn’t logged in, a signup/login modal appears. They can quickly create an account (or log in if they have one). We might allow social SSO (Google, Slack) for convenience.
	•	After auth, if an agent requires a purchase or subscription, we present a pricing plan selection (especially if there are tiers or a trial). The user confirms and proceeds to payment.
	•	The payment can be via Stripe for credit card (we’ll integrate Stripe Checkout for simplicity) or via crypto if they choose – in which case we use NowPayments or a similar gateway to handle crypto transactions. For crypto, we’ll likely only enable it on the live site (in demo it would just simulate). The key is to offer both options and mark them clearly (e.g., “Pay with Card” vs “Pay with Crypto”).
	•	During this flow, the agent they selected is remembered, so that upon completion, we know which agent to deploy for them.

2. Post-Purchase Deployment: After successful payment (or if the agent is free, after signup), the agent will be deployed into the user’s dashboard:
	•	In our backend, this means creating an instance of that agent tied to the user’s account. In the UI, once the user enters the app, they’ll see that agent in their “My Agents” list.
	•	We’ll likely redirect the user directly into their new Dashboard with the agent’s panel open. For example, they might land on a dashboard page (web app environment) where the agent they just deployed is highlighted with a “Setup your new agent” prompt.
	•	We will carry over any relevant info from the demo: e.g., if during the demo they filled out some profile info or actually created a lead, we could ask if they want to import that into their agent’s data. (To keep it simple, we might not carry over chat transcripts unless explicitly useful, but we could use it to personalize initial settings.)

3. Harmony Dashboard Key Features: The full dashboard (Harmony OS App) is a more robust interface where the user can manage all their agents and see real performance data. According to our design blueprint, this dashboard will include:
	•	Overview Tab: A high-level view of all active agents and key business KPIs (sales, leads, tasks done). For instance, a chart of Sales vs Leads over time, and summary cards for each agent’s contributions ￼ ￼. This gives immediate value and insight when the user logs in.
	•	Agents Tab: A section listing each agent the user has deployed (with possibly an option to “Add new agent” from marketplace for the future). Each agent entry could show status (running/paused), recent activity, and a “Manage” button. Clicking an agent takes the user to that agent’s detailed page or opens its console.
	•	On an agent’s detailed view, the UI might look similar to the demo page (chat on left, stats on right), but now it’s persistent and using the user’s real data. The user can configure agent settings here (integrations, thresholds, etc.), view logs specific to that agent, and start/stop the agent.
	•	Settings/Integrations Tab: A place for the user to manage account-wide settings. This includes managing their connected integrations (e.g., reconnect or disconnect HubSpot, Slack, etc.), API keys, billing info, team members (if multi-user accounts), and so on ￼ ￼. For example, if the user wants to connect a new integration after initial setup, they go here.
	•	(Possibly) Marketplace/Subscription Tab: If the user wants to deploy additional agents, a marketplace interface (could be a modal or a separate page) will let them browse available agents (including those that were locked in the demo) and initiate purchase/deployment for those.

The design for the dashboard will follow the same Harmony design language, but with a bit more emphasis on data display and management controls (since it’s a working app, not just a demo).

4. Payment Integration (Stripe & Crypto): On the live dashboard, when a user chooses to deploy an agent that costs money (one-time or subscription), we will integrate:
	•	Stripe for traditional payments (we can use Stripe’s subscription API if it’s a recurring SaaS fee, or one-time charge if it’s a one-off purchase). The flow should be seamless: likely a popup checkout or redirect that brings them back.
	•	NowPayments (or similar) for crypto payments, if offered. This would let the user pay in various cryptocurrencies. We’ll have a clear UI for it because crypto transactions might take longer to confirm. Possibly, if crypto is chosen, we’d provision the agent as “pending” and only activate once we get payment confirmation via webhook.
	•	Both methods will be available in the app’s billing settings as well, so the user can manage their subscriptions or top-ups. For the demo conversion specifically, we ensure that all test mode flags are off when in production – i.e., live Stripe keys for real charges, and live NowPayments API keys.

5. From Demo to Live Data: We also want to handle the user’s data transition:
	•	Any data captured during the demo (e.g., the lead info the user entered to test CA$H) will be treated as demo data and not automatically merged into their live CRM unless they choose to. We may prompt: “You entered some sample data during the demo. Do you want to save any of it?” Most will likely say no, but offering to carry over the conversation transcript as a “Getting Started Guide” for the agent could be a nice touch.
	•	The user’s integration credentials provided in the demo (if any) should carry over to their account so they don’t need to reconnect. We will securely save those upon account creation if the user gave permission. Otherwise, once in the dashboard, they’ll be prompted to connect integrations again to fully activate agent capabilities.

6. Ongoing Agent Management: After deployment, the user can interact with the agent in their dashboard similarly to the demo (chatting with it, asking it to perform tasks) but now everything is real. The agent will operate continuously or on triggers, not just via chat. The dashboard might allow the user to set the agent’s automation rules (for example, CA$H could be set to auto-reply to new leads 24/7). Designing the interface for those configurations and showing performance over time will be part of the full build-out.

7. Analytics & Feedback: We will instrument analytics throughout the demo and conversion process:
	•	Track events like demo_view, agent_selected, mode_toggled, phase_completed (strategy/execution), cta_click (which CTA), signup_complete, payment_complete. This helps us refine the funnel. These events can be sent to an analytics service or logged for our review.
	•	Post-deployment, the app will track agent usage (e.g., how many leads did CA$H handle this week) and possibly show those on the dashboard (good for proving ROI).

8. Roadmap for Full Build-Out: According to our internal plan, the Harmony OS App + Dashboard is the top priority as a flagship product. It entails building the login system, the main dashboard UI, agent management pages, and underlying logic for agent orchestration ￼. We will use a modern tech stack (likely React/Tailwind for front-end, Node/Express or Next.js for backend, plus integration SDKs). After that, the Agent Marketplace web portal (for browsing and adding agents) and the Marketing website will follow ￼ ￼, but those can be informed by the demo’s success.

Finally, ensure that with each step from demo to full app, the user experience is smooth: the user should feel like they are simply unlocking more of the same system. The demo page, the sign-up flow, and the dashboard should all feel like parts of one cohesive Harmony platform. By carefully designing the hand-off (demo CTA -> account creation -> agent appears in dashboard), we convert curiosity into lasting engagement.
