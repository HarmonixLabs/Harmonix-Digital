Harmony Platform – Full Deployment Prompt for Replit AI Developer

You are now the lead AI developer (Replit Agent) tasked with building Harmony, a next-generation multi-tenant AI platform from the ground up. This prompt provides the complete blueprint (Steps 1–45 of the Harmony Build Plan) for a production-ready system, integrating all frontend, backend, and AI components. Follow the specifications precisely to autonomously develop the platform and maintain it via continuous self-healing.

🧠 Overview & Vision

Harmony is a sovereign AI-driven ecosystem composed of 12+ intelligent agents (Digital Team Members) working in concert under one platform. Each agent has a specialized domain (Sales, HR, Project Management, etc.), and the Harmony Core orchestrates their collaboration. The platform is multi-tenant (supports many organizations), modular, and designed for performance, beauty, and depth – aligning technical excellence with Harmonix’s spiritual and design principles.

Core philosophy: “Never replace humans – empower them.” Each AI agent augments human teams, operating like digital colleagues rather than bots. The system should scale across Web, Desktop, and Mobile, delivering a seamless cross-platform experience.

🎯 Objectives & Requirements
	•	Full-Stack MVP: Build the complete Harmony platform MVP including frontend UI, backend APIs, database schema, and AI agent logic.
	•	Multi-Tenancy: Support multiple businesses and user accounts with data isolation and tenant-specific customizations (branding, subdomains, etc.) ￼.
	•	Agent Orchestration: Implement the Harmony Core engine to route tasks and messages between agents (e.g., Sales agent handing off a lead to Concierge agent).
	•	Integrations: Enable connections to external services (Google Workspace, HubSpot, ClickUp, Stripe, Calendars, CRM systems, Slack, Notion, etc.) so agents can act across tools.
	•	Modularity: Architect the system for easy addition of new agents, integrations, and UI modules. All components should be loosely coupled and extensible.
	•	Branding & UX: Adhere to the Harmonix Design System – a Timeless Futurism palette (Forest Green & Gold accents) with elements of sacred geometry, golden ratio layouts, and “Divine” branding guidelines. The UI must be clean, modern, and conversion-optimized.
	•	Quality & Security: Enforce best practices (rate limiting, 2FA, JWT auth roles, input sanitization) and ensure the platform passes penetration tests (OWASP ZAP compliance, etc.).
	•	Self-Healing: Implement autonomous monitoring and repair mechanisms to detect and fix issues in real-time without human intervention (broken pages, errors, code regressions, etc.).
	•	Scalability: Prepare for cloud deployment (Vercel for frontend, Railway or similar for backend) and eventual mobile/desktop apps. Optimize for performance and future multi-tenant scaling (efficient queries, caching, load balancing).

🏗️ Tech Stack & Architecture
	•	Frontend: Next.js (React) application for the web UI, using TypeScript. Leverage Next.js for server-side rendering and API routes where appropriate. The UI will follow the Harmonix Design System (special edition Forest Green & Gold theme) to ensure brand consistency.
	•	Backend: Node.js with Express (or NestJS) for building RESTful APIs and backend logic. Use a modular structure (e.g. NestJS modules or Express routers) to separate concerns (auth, agents, marketplace, admin, etc.).
	•	Database: PostgreSQL as the primary datastore (using an ORM like Prisma or TypeORM). Structure the schema for multi-tenancy (e.g. each core table has a tenant_id for data partitioning). Ensure transactional integrity and use indexed relations for performance.
	•	AI Integration: OpenAI GPT-4 (via API) as the core LLM for agent intelligence. Integrate LangChain in the backend to manage prompts, agent chains, and tool usage logic ￼ ￼. This provides a framework for building complex AI behaviors (memory, retrieval, chaining calls) within Node.js.
	•	Agent Runtime: Each AI agent is implemented with a combination of prompt templates, tools (integrations), and logic scripts (possibly using LangChain Agents or custom logic). Agents communicate with the Harmony Core via event messaging or an internal API.
	•	Cloud & DevOps: In Replit, run the Node backend and Next.js frontend concurrently (if using a monorepo, ensure Replit can start both, possibly with npm run dev for frontend and a separate process for backend). For production, plan deployment on Vercel (frontend) and Railway or AWS (backend & DB). Use environment variables for configuration (API keys, DB URLs, etc.). Provide docker-compose or deployment scripts for easy provisioning later.
	•	Styling & Components: Use the Harmonix UI component library (if provided) or build a custom component library matching the design board. Utilize CSS-in-JS (styled-components or CSS modules) to implement the Timeless Futurism aesthetic and responsive design.

1. Frontend UI – Next.js React Application

Design a Next.js frontend that delivers a polished, intuitive interface for all user interactions. Key requirements:
	•	Harmonix Design System: Implement the special edition theme with Forest Green primary and Gold accents. Ensure consistent typography, spacing, and use of sacred geometry motifs (e.g., subtle geometric background patterns) and golden ratio proportions for layout balance ￼. By using the golden ratio in web layout, the interface will feel naturally balanced and pleasing to users ￼.
	•	Responsive & Cross-Platform: Use mobile-first responsive design so that the web app can function on desktop, tablet, and mobile browsers. In the future, this can be wrapped as a mobile app (React Native or Expo) and a desktop app (Electron), so design with adaptable components.
	•	Page Structure: Scaffold all major pages and routes:
	•	Dashboard Home: Overview of user’s agents and key metrics.
	•	Agent Detail Pages: For each agent, a page with agent description, status, chat interface, settings/configuration panel.
	•	Marketplace: A marketplace page listing available agents (with search, filters, categories), including both Harmonix-built agents and community submissions.
	•	Launchpad/Onboarding: A guided setup page for new users (see Launchpad section) and an integration hub for connecting external services.
	•	Admin Panel: (Accessible to super-admins and tenant admins) for managing platform-wide and tenant-specific settings.
	•	Authentication pages: Signup, login, 2FA verification, wallet connection page, etc.
	•	Demo & FAQ pages: A library of interactive demos and a rich FAQ page.
	•	State Management: Use React state (or Context/redux if needed) to handle global UI state (e.g., current user, theme). Leverage Next.js API routes or separate API endpoints for dynamic data (e.g., fetching agent responses, metrics).
	•	Components & UX: Build reusable components such as:
	•	Navigation sidebar or topbar with menu (conditionally showing Admin controls if role permits).
	•	Agent “cards” or tiles that display each agent’s status, with toggles to enable/disable and quick info.
	•	Chat interface component (showing message history between user and a selected agent).
	•	Forms for settings (e.g., agent prompt customization, integration keys).
	•	Modal dialogs for confirmations (e.g., purchasing an agent, confirming an action).
	•	Special UI Elements: Adhere to visual anchoring techniques – important actions should be highlighted (e.g., “+ New Agent” or “Launch Launchpad” buttons). Use color psychology in UI: Forest Green for trust, growth; Gold for highlights and interactive elements, conveying premium quality.
	•	Frontend API Integration: The frontend calls backend API endpoints securely (with JWT tokens in headers or using Next.js API routes as a proxy). Ensure proper error handling and user feedback for loading states, errors, successes.
	•	Internationalization (future-ready): Although initial release is likely English, structure the frontend text and labels in a way that adding i18n (multiple languages) is straightforward later on.
	•	Accessibility: Follow accessibility best practices (ARIA labels, keyboard navigation, contrast compliance) so the UI is usable by all. Provide dark mode toggle if time permits (or at least ensure color choices are accessible).

2. Backend APIs & Logic – Node.js/Express Server

Develop a robust Node.js backend (preferably with Express or NestJS) providing RESTful APIs for all frontend actions and implementing core business logic:
	•	REST API Structure: Organize endpoints with clear routing. For example:
	•	/api/auth/* for authentication (login, signup, OAuth callbacks, 2FA verification).
	•	/api/agents/* for agent-related actions (list agents, get agent state, chat with agent, configure agent).
	•	/api/marketplace/* for marketplace actions (list available agents/templates, purchase/mint agent, list user’s purchased agents).
	•	/api/admin/* for admin and governance (manage users, override prompts, review content, etc.).
	•	/api/integrations/* for initiating OAuth or saving integration tokens (Google, Slack, etc.).
	•	/api/metrics/* for retrieving metrics and analytics data.
	•	Database Models: Define the PostgreSQL schema and corresponding models/ORM entities. Key tables (with suggested fields) include:
	•	Tenant – id, name, domain, logo, theme, created_at, ...
	•	User – id, tenant_id, name, email, password_hash, role (admin/manager/member), wallet_address (if Web3 login), created_at, ...
	•	Agent – id, tenant_id, agent_type (e.g., Sales, HR, custom), status (active/disabled), config (JSON for custom prompts or settings), usage_stats, ...
	•	AgentTemplate – id, creator_user_id, name, description, price, royalty, category, config_schema, is_public, minted_nft_id (if applicable), ... (templates in the marketplace, which can be minted or cloned into Agents)
	•	IntegrationCredential – id, user_id/tenant_id, service (e.g., “google_calendar”), auth_type, token (encrypted), meta (e.g., refresh token, scopes).
	•	Subscription/Purchase – records of marketplace purchases or subscriptions to agents, for billing and royalty tracking.
	•	Message/Interaction – logs of interactions (agent conversations, etc.) if needed for metrics or debugging.
	•	AuditLog – (for admin) records of critical actions (overrides, agent updates, errors caught by self-healing, etc.).
	•	Metrics – could be aggregated on the fly, or store snapshots of metrics like time saved, ROI, etc., per user/agent.
	•	LangChain + GPT-4 Integration: Within the backend, set up a module for AI interactions:
	•	Use LangChain (or a custom service class) to manage calls to OpenAI’s GPT-4. For each agent request, construct prompts that incorporate the agent’s persona, recent conversation context, and relevant data.
	•	Integrate tools via LangChain’s tool interface or custom logic: e.g., the Sales agent might use a CRM API tool, the Project Manager agent might query ClickUp API, etc.
	•	Maintain short-term memory per conversation (could store in session or DB) and consider using vector stores for long-term memory if needed (though MVP can keep it simple with recent messages).
	•	Implement a basic Harmony Core Orchestrator: a function or service that can take events or outputs from one agent and route them to another. For example, if the Sales agent flags a new lead, the Core triggers an action for the Concierge agent to follow up. This can be rule-based initially (if X event, call Y agent) and later learned or customized by admins.
	•	Express Middleware & Structure: Use middleware for:
	•	Auth: Verify JWT on protected routes, attach req.user and req.tenant based on token. Enforce role-based access on admin routes.
	•	Input Validation: Validate request bodies (using something like Joi or Zod) to prevent bad data or injection.
	•	Error Handling: Global error handler to capture exceptions and return standardized error responses.
	•	Rate Limiting & Security: Apply rate limit on APIs (especially agent chat endpoints to prevent abuse). Sanitize inputs to prevent SQL injection or XSS (though parameterized queries in ORM handle SQL injection).
	•	Integration Hooks: Set up integration connectors for the services outlined:
	•	For each supported integration (Google, HubSpot, ClickUp, Stripe, Calendars, Phone/SMS, CRMs, Slack, Notion, etc.), create either dedicated modules or use SDKs/APIs. For OAuth-based services (Google, HubSpot, etc.), implement OAuth 2.0 flows:
	•	Provide endpoints like /api/integrations/google/calendar/connect that initiate OAuth and /api/integrations/google/callback to receive auth code and store tokens.
	•	Store tokens in IntegrationCredential and ensure encryption for secrets. Notify the user on the UI of success/failure.
	•	Agents that require a certain integration (e.g. Calendar Agent needs Google Calendar access) should check for credentials and prompt the user if missing. For MVP, you can simply have the UI or agent response indicate “Please connect your Google Calendar to use this feature.”
	•	Stripe integration: For payments in the marketplace, integrate Stripe Checkout or Stripe API to handle purchasing an agent or subscription. Webhooks from Stripe should be handled to confirm payments and activate purchased agents.
	•	Phone/SMS: For 2FA and possibly for agents (if an agent needs to send SMS), integrate a service like Twilio (if available) or an SMS API. Ensure 2FA codes can be sent via SMS or email.
	•	Agent Execution & Sandbox: When an agent is invoked (e.g., user asks a question in chat to an agent):
	•	The backend should receive the request, identify which agent and which user/tenant, then construct a prompt for GPT-4 via LangChain. Include system/context messages that reflect the agent’s persona and any organizational knowledge. For example: “You are SalesAgentGPT, a sales assistant for [TenantName]. Your role is to generate leads and respond in a friendly manner…”.
	•	If the agent needs to use a tool (like schedule a meeting via Google Calendar), the system either intercepts the request via LangChain’s tool system or by parsing the GPT output for a known pattern (e.g., a special format indicating an action). Implement at least a mock version of tool use for MVP (e.g., agent can “request” an action and the backend simply logs it or returns a dummy success).
	•	Ensure that if GPT output might contain sensitive or malicious content, apply a filter (OpenAI API has a moderation filter; also consider your own checks).
	•	Performance considerations: Use caching for repeated requests where possible. For instance, if multiple users frequently request the same FAQ answer or agent response, cache it. Optimize DB queries with proper indexing, and use a scalable connection pool.

3. AI Agent Architecture & Marketplace Logic

Build the infrastructure for managing multiple AI agents, including an Agent Builder, a Marketplace for agents, and support for NFT minting and licensing of agents:
	•	Agent Builder & Configuration: Allow super-admins (or eventually end-users) to create or configure agents:
	•	Define a standardized format for an agent profile: including the base prompt (persona/role), the tools/integrations it can use, and parameters (e.g., temperature for creativity, any guardrails).
	•	Provide UI forms to adjust an agent’s behavior (in the Agent Dashboard UI, as mentioned). This should update the agent’s config in the database.
	•	Agents can be “private” (visible only to the creating tenant) or “public” (submitted to the marketplace for others). Include a flag for public/private.
	•	If agents can be created via a no-code interface, support basic editing of prompts and selecting integrations. (For MVP, manual JSON config editing or simple forms is fine.)
	•	Agent Marketplace: Implement a marketplace where agents (or agent “templates”) can be published, discovered, and acquired:
	•	The Marketplace page (frontend) should display a catalog of agents: each with a name, description, publisher (Harmonix or community user), stats (e.g., how many users or ratings), price or subscription fee, and whether it’s included in one’s plan.
	•	Provide filters/search by category (sales, support, etc.) and a detail view for each agent with a bio, use-case examples, demo link, stats, and user reviews.
	•	Purchase/Install Flow: A user can click to install/buy an agent. If free, it simply adds the agent to their account (creates an Agent entry from the template). If paid, process payment via Stripe (or crypto in future) then add the agent. If NFT-based, the purchase could mint an NFT token representing the license (but for MVP, this can be a placeholder concept).
	•	NFT Minting & Licensing: For special “limited edition” agents or to enable reselling, integrate with an NFT platform or use a library like web3.js or ethers.js for Ethereum:
	•	When an agent template is minted, create an NFT on a blockchain (could be testnet or a platform like Polygon). Store the token ID in the AgentTemplate.
	•	Owning the NFT could confer the right to use that agent. The platform should verify NFT ownership (e.g., via wallet login) for those particular agents.
	•	Support royalty splits: If a community creator sells an agent template, they receive a percentage of revenue (e.g., via Stripe Connect or by the platform accounting). This will require tracking sales and payouts.
	•	If an agent template is resold (secondary market), enforce royalty to original creator if applicable (this can be done with NFT royalty standards or internally track transfers).
	•	Subscriptions & MRR Tracking: Many agents might be sold on a subscription basis (monthly fee). Implement backend logic to handle subscriptions:
	•	Possibly use Stripe subscriptions. Track MRR (monthly recurring revenue) per agent and for the platform.
	•	Show users their current subscriptions in a dashboard, allow cancellation or upgrades.
	•	Ensure that disabling a subscription removes access to the agent after the paid period.
	•	Royalty calculation: e.g., if a community agent has a 20% royalty to Harmonix, and it has X subscribers at $Y/mo, compute payouts accordingly.
	•	Usage Stats & Ratings: Each agent should report usage (e.g., number of queries handled, time saved, satisfaction rating). Implement an endpoint to log when an agent completes a task or when a user gives feedback. Display these stats in the agent’s marketplace listing (e.g., “1200 hours saved”, “Rating 4.8/5 from 30 users”). Usage stats underscore value for marketing.
	•	Public/Private Toggle: A user (or admin) who creates an agent can choose to publish it. When an agent is private, only their tenant can use it. If public, it appears in marketplace. For MVP, maybe only super-admins can publish to marketplace to ensure quality.
	•	Agent Execution Environment: If applicable, consider sandboxing agent logic (for example, if allowing community-created Python code, run it in an isolated container). However, MVP likely uses only GPT-4 and preset integrations, so code injection risk is low, but keep in mind for future if users upload custom code.
	•	Agent Governance: In the admin layer (discussed below) include controls like:
	•	Ability for super-admin to veto or remove an agent from marketplace (e.g., if inappropriate).
	•	Mechanism to push prompt updates: if Harmonix improves an agent’s prompt or logic, it should sync to all users using that agent (unless they opted out or forked it).
	•	Versioning: Agents should have version numbers. If an update is available, notify admins/users and allow update (or auto-update if minor). Maintain backwards compatibility where possible.
	•	Example: An existing AI agent marketplace (e.g. Synergetics’ AgentTalk) allows creators to set fixed prices, subscriptions, or royalties for their agents ￼. Use similar best practices: integrate a payment layer so creators earn income when their agent is cloned or subscribed to ￼. Ensure each agent listing clearly shows required integrations/permissions and offers one-click install for users ￼ ￼.

Include an interface to edit the prompt/parameters and a mechanism to notify or auto-sync the changes. (This is critical for quickly fixing agent behavior issues or doing global improvements).
	•	Override Protocol: If an agent is misbehaving or a tenant requests changes, super-admin can apply an override – e.g., forcing a particular output, or disabling a certain feature of an agent across the board. Log these overrides in the AuditLog for transparency.

	•	Tenant Admin Panel: Within their own tenant context, admin users can:
	•	Manage their users (invite, remove, assign roles).
	•	Customize their branding – e.g., upload logo, set theme colors (which can override default colors on their subdomain).
	•	Manage their agents: enable/disable certain agents, configure default prompts or connections, purchase new agents from marketplace.
	•	View their usage metrics and ROI dashboard (time saved, etc.).
	•	Manage billing: see their subscriptions (to Harmonix platform or specific agents), update payment info.
	•	Oversee data integration: e.g., connect the company’s Slack, or disconnect an integration.
	•	Agent Updates: If Harmonix pushes an update to an agent, the tenant admin could have an option to review changes (if needed, accept or postpone). Also allow them to customize an agent’s prompt for their org (within limits) – for instance, they might add a company-specific greeting or knowledge base.
	•	Update/Veto Logic: Build in logic so that:
	•	A super-admin can veto an action by an agent if it seems harmful. This could be manual (monitoring live agent interactions) or automatic (if Ethical AI module flags something). For MVP, a manual kill-switch: e.g., super-admin can deactivate an agent globally or for a specific tenant.
	•	If an agent is updated (prompt changes, new version), and a tenant heavily modified it, decide how to merge or allow them to continue on the old version if they choose.
	•	Syncing Agents: If the system has offline or external components (like future mobile apps), ensure that admin changes (like disabling an agent or updating a prompt) are propagated to all running instances or sessions. This likely involves the backend as source of truth and the frontend polling or using WebSockets to get updates.
	•	Audit & Logging: Everything the admin does should be logged (who did what and when). Also, major agent actions (like auto-email sent, file generated) could be logged for later audit. Provide an interface for admins to view these logs with filters (by agent, by user, by date).
	•	Admin UX: The admin interface should be user-friendly despite its power. Use clear warnings and confirmation dialogs for destructive actions (like deleting a tenant or agent). Provide search and filters for large data (e.g., searching users, filtering log entries).

5. Self-Healing System

Incorporate an autonomous self-healing mechanism that continuously monitors the platform for issues and resolves them without human intervention when possible. This is critical for maintaining uptime and code integrity as the AI will be continuously updating the platform.
	•	Heartbeat Monitoring: Implement a background service (could be a Node cron job or separate process) that pings critical pages and endpoints regularly to ensure they respond without errors:
	•	E.g., periodically make requests to each frontend route (via an HTTP request) and key API endpoints. If any respond with error or are unreachable, flag it.
	•	Similarly, run basic UI checks (if possible, use a headless browser or simple DOM checks on pages to verify important elements exist).
	•	Automatic Bug Detection: Leverage the Replit AI’s capabilities to detect anomalies in logs or performance:
	•	Watch for increased error rates, exceptions thrown, or pages returning 500s. The logging system should funnel these signals to the self-healing agent.
	•	Detect UI issues like missing components or broken links (for example, parse the rendered HTML for “Error” messages or check if all  sources loaded).
	•	If the code is updated by the AI itself (continuous development mode), detect if a recent change introduced duplicate code blocks or infinite loops by analyzing CPU/memory usage or repetitive log patterns.
	•	Healing Strategies: When an issue is detected, the system should attempt predefined fixes:
	•	Restart/Reload: If a service is hung or a page is not responding, attempt to restart the affected process (in Replit, ensure the server restarts on crashes).
	•	Rollback Changes: If a recent code change leads to failures, revert to a previous stable version. (This implies maintaining version control or at least keeping a backup of last good state).
	•	Hot Patch: For known simple issues (like a missing null check or a small logic bug that the AI can identify from the error stacktrace), allow the AI to modify the code live to fix it. Since this is autonomous, set boundaries or tests – e.g., run the failing scenario after the patch to verify it’s fixed.
	•	UI Regeneration: If a page is missing a component (say a new route was supposed to have a form but it’s blank or erroring), the self-healing could try to regenerate that component based on the intended design. This could be done by having the AI refer to the design specs and codebase to create the missing piece.
	•	Duplicate Code Cleanup: If looping or duplicate code is detected (e.g., two similar functions or infinite recursion), the system flags it. Possibly schedule a self-healing task where the AI refactors or removes duplicate logic.
	•	Notification & Logging: When the self-healing system intervenes:
	•	Log the incident in the AuditLog (what was detected, what fix was applied).
	•	Notify the development team or super-admin (e.g., via email or an admin UI alert) about the issue and resolution. Include before/after if code was changed.
	•	If the issue cannot be auto-resolved, escalate it: perhaps mark it for human review or temporarily disable the affected feature to keep overall system stable.
	•	Integrity Checks: Continuously verify the integrity of the codebase and database:
	•	For code, ensure critical files exist (no accidental deletion), check that tests (if any) pass after changes, and that the file structure matches what’s expected. If something’s missing, attempt to restore from template or ask the AI to rebuild it.
	•	For database, check for schema consistency (migrations applied), detect anomalies in data (like massive spikes in values that could indicate a bug).
	•	Example Use Cases:
	•	A page returns 404 because the route isn’t defined – the self-healing agent knows from the plan that this page should exist, so it generates the route and a basic component from the spec.
	•	The agent’s code goes into an infinite loop due to a logic error – detect high CPU and the repeated log line, automatically apply a fix (like add a break condition) using the AI coding assistant ￼.
	•	A third-party API integration breaks (e.g., API changed) – catch the error, and either auto-update the API call format if known, or disable that integration and notify developers.
	•	Self-Test Suite: As part of self-healing, develop a suite of automated tests or checks that run periodically:
	•	Simulate user flows (sign-in, create agent, use agent, etc.) either through integration tests or via a scripting of the AI to do so, to catch any regression.
	•	Use these tests as verification whenever new code is deployed by the AI.
	•	Goal: Over time, the platform should “heal” itself akin to self-healing software that identifies and fixes faults without human help ￼. This increases reliability and allows continuous deployment. Nonetheless, maintain a manual override (human can step in or disable the self-healing if it malfunctions).

6. Launchpad & User Onboarding

Implement a Launchpad module and an intuitive onboarding flow to help new users integrate their data and get up to speed, and to allow entrepreneurs to build new ideas within Harmony:
	•	Harmony Launchpad (Incubator Portal): This is a special section (as described in Build Plan Step 45) to empower users to create new AI-driven projects (apps, agents, products) on the platform:
	•	Provide an AI Business Builder wizard: a step-by-step guided funnel that takes a user’s idea and turns it into a plan or even a minimal agent MVP. For example, ask the user a series of questions about their idea (domain, target users, what it should do) and leverage GPT-4 to recommend an agent configuration or a set of agents to achieve it.
	•	Include a Launch Checklist Generator ￼: based on the idea, automatically generate a checklist of tasks to launch (branding needed, legal steps, marketing emails, funnel pages, etc.). This can use prompt templates to output a checklist and resources.
	•	Monetization Hub ￼: Provide integrations or pointers to set up payments for the user’s new idea. Possibly integrate Stripe or LemonSqueezy API so they can start charging for their own product built on Harmony. (For example, if they built an agent-powered service, how to bill end customers – could later tie into Harmony’s marketplace or a Stripe connect setup.)
	•	Partner Agent Network ￼: A section where users can hire freelance help (copywriters, devs, designers) for their projects. For MVP, this could simply list recommended partners or a contact form (does not need full implementation).
	•	Essentially, the Launchpad is a value-add to attract startups: it turns Harmony into not just an internal tool, but a platform to launch businesses.
	•	User Onboarding Workflow: When a new tenant signs up:
	•	Guide them through connecting key integrations relevant to their chosen agents. For example: “Connect your Google account” (for Calendar or Gmail agent), “Connect HubSpot” (if they enabled a Sales CRM agent), etc. Use a checklist UI that highlights which integrations are done and which are pending.
	•	If an agent requires an integration and it’s not connected, display a notification or alert in the dashboard (e.g., “Your Calendar Agent is offline until you connect a Calendar. Click here to integrate Google Calendar.”). This ensures users know why an agent might not fully function.
	•	Provide default Agent Setup: Possibly, during onboarding, let them choose which agents to activate (toggle from the 12 flagship ones). Pre-select a recommended set based on their industry if known. This will create those agent instances for their tenant.
	•	Provide a brief tutorial or demo inside the app – e.g., an interactive guide (maybe a step-by-step overlay) that introduces the dashboard, how to invoke an agent, where to find metrics, etc.
	•	Ensure the first-run experience is not overwhelming: perhaps hide advanced modules (Launchpad, etc.) until the user is ready or provide a “Beginner/Advanced” toggle.
	•	Integration Center: A unified page (or modal) listing all available integrations (Google, Slack, Stripe, etc.) with status (connected or not). From here, user can manage connections. This page ties into onboarding but remains accessible later via settings.
	•	Notifications: Implement notifications to guide users:
	•	If an agent tries to use a missing integration (e.g., booking a meeting but no calendar connected), catch that in backend and send a notification or real-time alert suggesting to integrate.

7. Authentication & Security

Implement a robust authentication system supporting multiple login methods and strong security measures:
	•	Account Creation: Users can sign up with email/password, and optionally via OAuth or wallet:
	•	Email/Password: Traditional signup with verification email. Store passwords securely (bcrypt hashing). Include “forgot password” flow with email reset link.
	•	OAuth Logins: Enable Sign in with Google (for convenience on web, plus ties into Google integrations), Sign in with Apple (for Apple device users), and possibly LinkedIn or other if relevant to target users. Use OAuth 2.0 flows and link the OAuth identity to a user account in DB (possibly allowing linking multiple methods to one account).
	•	Wallet-Based Login: Allow users to connect a Web3 wallet (like MetaMask) and use it for authentication. For MVP, this could mean using the wallet address as identity and signing a message to log in (to prove ownership). This is useful for NFT licensing: if an agent NFT is tied to a wallet, logging in with that wallet should give access. Use a library like ethers.js for signature verification.
	•	Ensure that if a user has multiple methods (say they signed up with email but later connect a wallet), their accounts merge or link properly rather than duplicate.
	•	Two-Factor Authentication (2FA): Offer 2FA for added security:
	•	Methods: SMS OTP, Email OTP, or authenticator app (TOTP). Implement at least SMS or email OTP for MVP.
	•	Upon login, if the user has 2FA enabled, prompt for the code. Integrate an SMS service for sending codes (Twilio or similar) ￼ or use email as fallback.
	•	Allow users to enable/disable 2FA in their account settings.
	•	JWT & Session Management: Use JWTs (JSON Web Tokens) for authenticating API requests:
	•	Issue JWT on login (and refresh tokens if implementing refresh cycle). Include user ID, tenant ID, and role in the token claims.
	•	Securely store JWT on frontend (HTTP-only cookie or memory if using Next.js secure SSR). If using cookies, implement CSRF protection.
	•	Enforce token expiration (and implement refresh token endpoint if not using cookie+session).
	•	On the backend, protect routes by verifying JWT and checking the role required.
	•	Access Control: Ensure that tenant isolation is enforced at every API call:
	•	When a request comes in, determine the tenant context (from JWT or subdomain or route).
	•	Every database query should be filtered by tenant_id (for tenant-specific data) unless the user is super-admin.
	•	Use an ORM’s middleware or manual checks to automatically inject tenant filters.
	•	Test that one tenant cannot access another tenant’s data by manipulating IDs, etc.
	•	Input Validation & Sanitization: All inputs from users (including prompts that will go to the LLM) should be handled carefully:
	•	Validate lengths and types to prevent injection or crashes (e.g., extremely long text).
	•	Sanitize outputs that will be rendered in HTML (to avoid XSS if any agent returns content).
	•	For any file uploads (if any feature allows file uploading in future, like training data), scan or restrict type.
	•	Rate Limiting: To prevent abuse (especially of GPT-4 API), apply rate limiting per user/IP:
	•	e.g., no more than N requests to the chat agent endpoint per minute unless on a high plan.
	•	Possibly tiered by subscription (free trial vs paid user).
	•	Use a library or simple in-memory counters for MVP.
	•	Logging & Monitoring: Keep audit logs of logins (successful and failed). Alert on suspicious patterns (multiple failed logins, etc.).
	•	Session Timeout: Consider auto-logout after a period of inactivity (especially for admin sessions).
	•	Testing Security: Before finalizing, run basic penetration tests:
	•	Check that route protections work (e.g., a non-admin cannot call admin APIs, etc.).
	•	Use OWASP ZAP or similar to scan for common web vulnerabilities (SQLi, XSS) ￼. Fix any issues flagged.
	•	Encryption: Secure sensitive data:
	•	Encrypt at rest any credentials or API keys stored (at least via application logic if not full DB encryption). For instance, integration tokens should be encrypted with a platform secret key.
	•	Use HTTPS for all requests (Replit dev might be http, but ensure production uses TLS – Vercel and Railway handle TLS by default).
	•	Wallet Integration Details: If wallet login is enabled:
	•	Provide a front-end flow: when user chooses “Connect Wallet”, use web3 to request signature of a nonce from the backend, then verify and log them in. Associate that wallet with a user account in DB.
	•	Use the wallet for any Web3 interactions like NFT checks: e.g., if a certain NFT is required for access, upon login check the blockchain (via web3 or an indexer) that the wallet has the NFT.
	•	Ensure to handle scenario where one user might have both email/password and a wallet – linking them to same account.
	•	Compliance: If targeting enterprise, ensure GDPR compliance (allow data deletion, etc. – see Compliance module in step 36 of build plan). Terms & Privacy pages should be accessible (static pages on frontend).
	•	Overall Security Stance: We aim for a defense-in-depth approach: robust auth, least privilege access, thorough validation, and continuous testing, to safeguard both user data and the platform’s integrity.

11. Final QA, Testing & Security Audit

Before launch, perform thorough QA (Quality Assurance) and implement safeguards:
	•	Functional Testing: Verify every feature against the requirements:
	•	Create test cases for user signup, agent chat, agent marketplace purchase, integration flows, admin actions, etc. Manually test or write automated tests for critical paths.
	•	Test with multiple tenants to ensure isolation (e.g., two test accounts should not see each other’s data).
	•	Test on different browsers and devices for frontend responsiveness.
	•	Edge Cases & Error Handling: Intentionally try to break things to ensure graceful handling:
	•	e.g., disconnect an integration while agent is mid-task, see how it responds.
	•	Try inputs that are at limits (max length fields, special characters).
	•	Simulate network issues (turn off internet to see app behavior, etc.) to see if proper messages show.
	•	Performance Testing: If possible, simulate load (especially on critical API endpoints like agent chats). Ensure the system can handle multiple concurrent users and that DB queries are optimized.
	•	Use dummy data to fill, say, 100 tenants, each with some agents and messages, and see if the dashboard loads quickly.
	•	Rate Limiting and Abuse Testing: Confirm that the rate limiting is effective:
	•	e.g., write a small script to hit an endpoint rapidly and ensure it starts returning 429 Too Many Requests after the limit.
	•	Check that an authenticated user of one tenant cannot change IDs in requests to access another tenant’s info (authorization enforcement).
	•	JWT & Role Enforcement: Ensure all protected routes indeed check JWT and user roles:
	•	Write tests where a normal user token tries to call admin API -> should be 403 Forbidden.
	•	Ensure expired tokens are rejected (and refresh works if implemented).
	•	Input Sanitization: Attempt an XSS attack via any input (like type <script>alert(1)</script> in profile name and see if it appears anywhere unsanitized).
	•	Test for SQL injection patterns in any API inputs (though ORM should mitigate, but good to double-check).
	•	Penetration Testing: Utilize automated tools like OWASP ZAP to scan for vulnerabilities ￼:
	•	Run ZAP or similar against a test deployment of the app. Review and fix any findings (common ones to check: missing security headers, any XSS, CSRF on forms if not using same-site cookies, etc.).
	•	If possible, do a code review for security issues or use a static analysis tool.
	•	Self-Healing Loop QA: Test the self-healing features in a controlled way:
	•	Intentionally break a minor thing (e.g., remove a component or introduce a known bug) and see if the self-healing agent detects and fixes it.
	•	Ensure it doesn’t overstep (like it shouldn’t change code that’s working).
	•	Validate that the logging and notifications for self-healing work.
	•	Final Polishing: Check content and branding:
	•	All pages should have proper titles, no “lorem ipsum” or placeholder text left.
	•	The color scheme and fonts are consistent. Use of Harmonix logo and any sacred geometry graphics is correct.
	•	Run a spell-check or language review on UI text and FAQs.
	•	Load & Scalability: While full load testing might be limited, consider future scaling:
	•	The architecture should allow horizontal scaling: e.g., stateless backend servers (sessions via JWT), so we can add more instances behind a load balancer.
	•	Database should be able to scale (maybe plan read replicas or partitioning by tenant if needed when huge).
	•	Next.js can leverage Vercel’s edge if needed for global performance.
	•	Backup & Recovery: Ensure procedures exist for backup (especially DB backups) and that you can recover if something goes wrong (for instance, if a self-healing change breaks something major, how to roll back? Possibly keep backups of code).
	•	Compliance Testing: If handling personal data, ensure things like account deletion works (user can request data deletion).
	•	Beta User Feedback: If time, run a closed beta with a few friendly users. Collect their feedback on any confusion or issues and refine.
	•	Go/No-Go Checklist: Before launch, go through a checklist of all critical items (security, performance, key features) and get sign-off (virtually, since AI is doing it autonomously, the checklist can be just in logs).
	•	Continuous Monitoring: Plan for after launch:
	•	Keep monitoring tools (server logs, error tracking like Sentry maybe) to catch any runtime issues in production.
	•	Use the self-healing and admin alerts to respond to any incident swiftly.

By ensuring rigorous QA and incorporating robust security measures, Harmony will be ready for production use and resilient against common threats.
